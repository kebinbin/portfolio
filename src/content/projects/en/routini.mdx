<TextBlock title="Why I built it">

Most React apps reach for React Router by default and inherit a whole framework along with it — loaders, actions, a data layer — when all they wanted was to map URLs to components. The genuinely small alternatives exist, but they tend to be hand-typed JavaScript with `.d.ts` files bolted on, not TypeScript-first.

**Routini is my answer to that gap:** a router that does routing and nothing else, designed around four hard constraints — a 9-export public API, zero runtime dependencies, TypeScript from the first line, and a bundle small enough to enforce in CI. I designed the API surface, wrote the internals, and built the documentation site that ships with it. It borrows modern API shapes from React Router and a minimalist instinct from the tiniest routers, but every line is my own.

</TextBlock>

<TextBlock title="The whole API on one screen">

The public surface is nine exports — small enough to read in a sitting, and the constraint that keeps the library honest.

- `<Router>` — the config wrapper. Takes a `routes` array, `<Route>` children, or both, plus opt-in `scrollRestoration` (top on forward navigation, restored position on back/forward — window-scoped by default, or pointed at a nested scroll container).
- `<Route>` — a route definition that renders nothing; it's tagged with a `Symbol.for` marker so detection survives production minification.
- `<Link>` — navigation that falls back to native browser behavior on modifier keys, non-primary clicks, or a non-`_self` target.
- `<Outlet>` — optional; renders the matched page inside a shared layout.
- `<Navigate>` — a declarative redirect that replaces history by default, so it never leaves a back-button trap.
- `useLocation()` — the current path plus an imperative `navigate()`.
- `useParams<T>()` — typed route params straight off the URL.
- `useSearchParams()` — a reactive `[URLSearchParams, setter]` pair.
- `navigate(to, options?)` — the same navigation, callable from anywhere.

A typical setup mixes an eager route, code-split routes, and a catch-all — no configuration, no build step:

```tsx
import { Router } from "routini";
import Home from "./pages/Home";

const routes = [
  { path: "/", component: Home },                        // eager — above the fold
  { path: "/artists/:id", lazy: () => import("./Artist") }, // code-split on demand
  { path: "*", lazy: () => import("./NotFound") },        // catch-all 404
];

export default function App() {
  return <Router routes={routes} />;
}
```

</TextBlock>

<TextBlock title="Lazy by default, code-split for free">

Lazy loading isn't an opt-in here — it's the recommended way to define a route. Any route can take a `lazy` thunk instead of a `component`, and Routini handles the dynamic `import()` and the Suspense boundary for you, with a per-route `loading` fallback or a global one on `<Router>`. Each page ships as its own chunk and is only fetched when its route actually matches.

Crucially, Routini **does not** use `React.lazy` under the hood. `React.lazy` always suspends for one frame on a component's first render — so even a route whose chunk is already cached flashes its loading fallback before the page appears. Routini resolves lazy chunks itself through a small state machine, so a warm route renders **synchronously**, with no skeleton flash. That detail is what makes preloading (next) actually pay off.

</TextBlock>

<TextBlock title="Instant navigation: preload + View Transitions">

Two features work together to make navigation feel immediate.

**Link preload** warms a route's chunk before the user commits to it, in whichever way suits the surface: `preload="hover"` fires on pointer-enter or focus, `preload="render"` schedules through `requestIdleCallback` so it never fights more important work, and `preload="viewport"` uses a *single shared* `IntersectionObserver` for every viewport link on the page rather than one observer per link. All three route through one module-level, `WeakSet`-deduplicated preloader, so a chunk is fetched at most once no matter how many links point at it.

**View Transitions** animate the navigation itself. Opting in per navigation (`viewTransition` on a `<Link>`, or `navigate(to, { viewTransition: true })`) wraps the commit in `document.startViewTransition`. The subtlety that took real work: the new route has to commit *synchronously* inside the browser's snapshot-animate-snapshot callback, which means forcing past React's batching with `flushSync` — remove it and the animation silently breaks, so it's guarded by a regression test. Give an element the same `view-transition-name` on both pages and the browser morphs one into the other:

```tsx
import { Link } from "routini";

// A feed card that morphs its artwork into the detail page's hero.
function ArtistCard({ artist }) {
  return (
    <Link to={`/artists/${artist.id}`} viewTransition>
      <img
        src={artist.photo}
        style={{ viewTransitionName: `photo-${artist.id}` }}
      />
    </Link>
  );
}
```

Back and forward inherit the same animation automatically. There's no call site to carry the intent on a browser gesture, so Routini records it in `history.state` when a navigation animates and replays it on `popstate` — symmetric transitions with zero extra API.

</TextBlock>

<TextBlock title="Resilience: a chunk-aware error boundary">

Code-splitting introduces a failure mode most tutorials skip: if a dynamic `import()` fails — a stale deploy, a dropped connection — Suspense doesn't catch it (it catches *suspension*, not *errors*), so the whole tree unmounts to a white screen. Routini wraps every route in an internal error boundary that catches both a failed chunk load and ordinary render errors.

It's exposed through two optional `<Router>` props — `errorFallback` and `onError` — and hands the fallback everything it needs to recover: `{ error, reset, reload, isChunkError }`. `reset()` drops the poisoned lazy entry and re-runs the import (React permanently memoizes a rejected `lazy`, so the module has to be replaced, not retried). And the boundary auto-recovers on navigation via a reset key, without remounting children — so a same-route param change keeps its state. Deliberately, Routini does **not** auto-reload or touch `sessionStorage`; that "self-heal" pattern needs persistent state to avoid reload loops and reaches well outside a router's job, so recovery is handed to the consumer, exactly as the bigger routers do.

</TextBlock>

<TextBlock title="The parts under the surface">

The small API sits on top of the pieces every router eventually has to get right.

The location store runs on React 18's `useSyncExternalStore`, not the usual `useState` + `useEffect`. That's not fashion — it closes a real race: effects run child-up, so a `<Navigate>` rendered in the initial tree fires its navigation *before* `<Router>`'s own effect attaches its listener, and the URL changes while the rendered route goes stale until a refresh. `useSyncExternalStore` reads the live snapshot after every commit and catches the drift automatically.

Route matching is **hand-rolled and dependency-free** — the last dependency, a regex-matching library, was dropped for a ~15-line segment matcher. Beyond removing a dependency, it's *safer*: no ReDoS surface, and a static segment with special characters (`/files/a.b`) compares literally instead of letting a stray `.` mean "any character." Matching is case-sensitive by design — the correct web default.

And `useSearchParams` is the export that keeps the whole thing coherent. Rather than widening the location store to the full URL — which would remount the matched route on every `?query` change — it keeps its own subscription and snapshots `window.location.search`. So the router's store stays **pathname-only**, and a query update re-renders the components that read it *without* tearing down the page. In the demo app this is the difference between a map that keeps its state and one that reloads on every pan.

</TextBlock>

<TextBlock title="Small on purpose — and provably so">

"Tiny" is a claim, so I made it measurable. Routini ships at **3.2 KB gzipped**, measured by a script in the repo that mirrors bundlephobia's method exactly — esbuild bundle, terser compress + mangle, then gzip/brotli — so the number on the landing page uses the *same* methodology as the competitor comparisons sitting next to it. CI fails the build if it crosses budget, which means a new feature has to earn its bytes or it doesn't land.

Underneath: **zero runtime dependencies** (only `react`/`react-dom` as peers), **~100 tests** across the matcher, navigation, popstate, lazy loading, dev-only warnings and the error boundary (Vitest + Testing Library + happy-dom), and **Changesets** so every user-visible change publishes with a changelog entry. It's ESM-first but ships CJS too, with hand-checked `.d.ts`/`.d.cts` outputs.

</TextBlock>

<TextBlock title="A playground for manual verification">

Automated tests catch regressions, but some things — does this View Transition actually look right, does hover preload really fire, does the error boundary's reset button behave as expected — need eyes on it, not just assertions. The monorepo carries a workspace-linked playground: a deliberately plain, unpublished app that exercises every export in isolation, one demo per sidebar entry, with the browser's Network and Console panels doing double duty as the test output — lazy chunks loading, preloads firing, `onError` logging, all visible in real time. It's the fastest way to confirm a change in the library didn't break the exact behavior it targets.

</TextBlock>

<TextBlock title="Naming and defaults">

A small surface means every naming and default choice carries weight, so several were argued out on the record.

`<Navigate>` was deliberately **not** renamed to `<Redirect>`, despite the recurring temptation: because it can also push (`replace={false}`), `<Redirect replace={false}>` reads as a contradiction, while `<Navigate replace={false}>` stays a coherent general-purpose primitive with a redirect-*safe* default. There's no `noMatch` prop — a catch-all `path: "*"` does the job, consistent with the ecosystem, and it *renders* at the current URL rather than *redirecting* to one (a distinction the landing page's own diagrams are careful to show). View Transitions are per-navigation, not a Router flag, because they freeze interaction while animating and their design lives in CSS, so the call site should decide. And competitor names appear in exactly one public place — the bundle-size chart, versions pinned in a comment — while everywhere else it's "a full-featured router," never a name.

</TextBlock>

<TextBlock title="A site that routes itself">

The whole marketing and documentation site is built with Routini and dogfoods nearly every feature it advertises. The homepage runs hero-through-footer as an eager route; the Docs and Examples pages are lazy, code-split, and preload on hover; a catch-all handles 404s. Everything lives under a required `:lang` prefix (`en`/`es`), with `/` redirecting via `<Navigate>` and an unknown language segment caught by a render-time guard — since constraining a param to `en|es` is intentionally out of scope. The Docs page is a react.dev-style two-column layout: a sticky sidebar that tracks the active section by scroll position, one section per export, and hash-anchored links that scroll smoothly even to a route whose chunk hasn't loaded yet. The Examples page complements it with copy-paste recipes for common patterns — a basic app, code-split routes, typed params — plus links out to full apps built with Routini, Sona among them. Code snippets across the site are highlighted at *build time* with Shiki, so the syntax highlighter never ships to the browser.

</TextBlock>

<TextBlock title="Where it stands">

Routini is **published on npm and live at [routini.dev](https://routini.dev)**. It's still pre-1.0 — feature-complete against its own roadmap, but deliberately held back from a 1.0 until the API has been exercised by someone other than me. The first release was gated on shipping a real app built with it (see Sona, next), so it went out proven against a production-shaped UI rather than only its own test suite.

The one capability under active reconsideration is **nested routes with shared layouts**: long kept out of scope to protect the size budget, it's the single thing a genuinely small router still tends to need, and the demo app's single-layout ceiling is the clearest evidence for it. `ssrPath` just keeps `Router` from crashing if it's ever rendered where `window` is undefined — a safety guard, not real SSR support, which (along with a `@routini/vite-plugin` for file-based routing and a small active-link helper for `<Link>`, so consumers stop hand-rolling `aria-current`) is still on the roadmap.

</TextBlock>
