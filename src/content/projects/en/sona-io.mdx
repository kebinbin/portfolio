<TextBlock title="A front end built to put Routini under load">

Sona is a front-end application for discovering local music: hearing an artist before reading about them, seeing where they play next and who shares that stage, and giving independent artists a route to nearby audiences. I designed it end to end in Figma, then built it in React 19, TypeScript and Tailwind CSS v4.

It exists because a documentation site cannot put a router under real pressure. [Routini](/en/projects/routini)'s own site is a handful of mostly static pages: it never holds audio across a navigation, never keeps an expensive map instance alive through a query-string update, and never has to recover from a chunk that fails on a route someone is already looking at. Sona does all three in one stateful shell, which is how I found out where the router actually bends.

The scope stops at the front end deliberately. Every artist, event, venue and distance comes from a seeded fixture that ships with the code, and "near you" is staged rather than measured. Putting a real backend behind it would have added a second system to debug without changing any of the routing, animation or state handling the front end had to get right.

</TextBlock>

<TextBlock title="One shell, three ways to discover">

Everything sits inside a single persistent frame: a top bar with search and an activity bell, a "For you" sidebar on desktop, the routed content, and a footer that holds the player. On small screens a tab bar replaces the sidebar. A segmented control switches between three routed lenses over the same near-you dataset:

- **Artists** — sorted by simulated distance (*"0.9 km · May 10"*), each card with a follow heart, switchable between immersive, list and grid layouts.
- **Events** — every upcoming show as its own card, and the mobile "Events" tab.
- **Map** — those same events placed geographically on an interactive map.

The three lenses are routes over one data model, sharing a sticky header. Selecting any artist or event navigates to a full detail page.

</TextBlock>

<TextBlock title="The persistent player and Routini's optional Outlet">

The player keeps playing while the rest of the application navigates. That follows from one Routini decision: `<Outlet>` is optional and layout belongs to the consumer. The player and the navigation sit outside the Outlet, so a navigation swaps only the page and the audio element is never in the part of the tree that unmounts:

```tsx
import { Router, Outlet } from "routini";

export default function App() {
  return (
    <Router routes={routes}>
      <TopBar />
      <main>
        <Outlet />   {/* only this swaps on navigation */}
      </main>
      <Player />     {/* lives outside the Outlet → keeps playing */}
      <BottomNav />
    </Router>
  );
}
```

Playback state (current song, queue, volume) lives in a small store. The player renders in two layouts, a compact mobile bar and a three-column desktop version, both built on a Radix slider, with a reserved artwork slot that keeps the footer from shifting when a track loads.

</TextBlock>

<TextBlock title="Detail pages, and the morph between them">

Selecting an artist morphs their feed photo, name and next-show date into the hero at the top of their page. It is a shared-element View Transition matched by `view-transition-name`. From there the page is plain content: a tracklist, upcoming shows, and co-performers derived from shared event line-ups instead of hand-authored lists.

The event page extends the same pattern. Its hero places a blurred, full-bleed copy of the poster behind the sharp artwork, and the `poster-<id>` name is shared between the events grid, the map popups and the hero, so all three morph into each other. No animation library is involved; the matching names do the work.

</TextBlock>

<TextBlock title="The map and the pathname-only store">

The Map lens renders one pin per **venue** so co-located shows do not stack, and hovering a pin opens a themed popup built from the same card used elsewhere, which means its poster morphs into the event hero as well. When a venue hosts several shows, a small `‹ 1/2 ›` control cycles them in place.

The viewport is held in the URL. `?lat&lng&z` is written to the query string on every pan and zoom through Routini's `useSearchParams`. Because the location store is **pathname-only**, writing that query does not remount the Leaflet instance underneath it. A router whose store tracked the whole URL would destroy and rebuild the map on every drag. This is the one place in the project where that store design is visibly load-bearing.

</TextBlock>

<TextBlock title="Follows and the activity feed">

A heart on the feed and on every artist page toggles a persisted follow, and the "For you" activity feed is derived from those follows: new shows and releases from followed artists, in the desktop sidebar and behind the mobile bell.

These rows skip the View Transition on purpose. A circular avatar does not morph cleanly into a horizontal hero the way the feed's rectangular artwork does, and knowing where to stop animating is part of the design. The page also replaced an earlier notifications master–detail pattern that only ever worked as a workaround under Routini's flat routing, which is a fair indication of where the router's limits sit.

</TextBlock>

<TextBlock title="How Sona exercises Routini">

Most of the router's capabilities are used here under realistic conditions:

- **Lazy and preload** — every route below the eager Artists feed is code-split and preloads on link hover, so navigation resolves without showing a loader.
- **`errorFallback`** — a custom fallback separates a failed chunk load, usually a stale deploy, from an ordinary render error, and offers the matching recovery for each: "Reload" for a stale chunk, "Try again" otherwise, with a `<Link>` back to the feed in both cases.
- **Shared-element View Transitions** — the feed-to-artist and poster-to-event morphs, wired with matching `view-transition-name` values.
- **`useParams`** drives the artist and event pages. **`useLocation`** decides when the sidebar drops for a full-width layout and which lens is active. **`<Navigate>`** handles the root redirect to `/artists`.
- **`useSearchParams`** keeps the map's viewport in the URL without remounting it.
- **`scrollRestoration`** — scoped through `scrollContainer` to `AppLayout`'s own scrolling `<main>` instead of the window, so switching lenses starts each lens at the top and navigating back into a list restores its previous position.
- **The optional `<Outlet>`** is what allows the player to persist across every navigation.

The fixture is small and fixed: eighteen artists, fourteen events and twelve venues come from a seeded generator and are imported statically, so "performing soon with" and "other events at this venue" are derived from that data, distances are assigned, and the dataset stays stable across regenerations. The songs are real audio files. The theme is a `data-theme` toggle applied before first paint, so the page does not flash on load.

</TextBlock>

<TextBlock title="Where it stands">

Sona is deployed and public. It runs a persistent player, code-split routes, shared-element View Transitions and live URL state on a 3.2 KB router, all four at once, which is what it was built to establish.

It also shows the limits. The persistent-player pattern depends on Routini having exactly one `<Outlet>` per application, and there is no way yet to nest a second layout with its own outlet inside the first, which a settings or admin section usually needs. That is the strongest in-application case for nested routes. A few exports stay unexercised here as well: `navigate()`, and the `render` and `viewport` preload modes.

Sona runs on a seeded fixture, with no live data layer behind it. Real geolocation in place of assigned distances, persistence behind follows, a submission surface for independent artists, and RSVPs with ticket links are the next phase, and none of them change the front-end architecture the project was built to test.

</TextBlock>
