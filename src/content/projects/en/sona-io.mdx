<TextBlock title="What Sona is">

Sona started as a Figma design — a personal exercise to sharpen my UI and product design skills — exploring one idea: discover local music by *listening* first, not by scrolling flyers — see where an artist plays next, who shares that stage, and give independent artists a way to reach nearby audiences. It's a hypothetical product; whether it ever becomes a real service is an open question.

What it **is** today is a genuine front-end and nothing more: designed end-to-end in Figma first, then later built from that file in React 19, TypeScript and Tailwind CSS v4 — once the design was done, building it for real became the natural next step to give [Routini](/en/projects/routini), the tiny router I wrote, a genuine testing ground. There's no backend — every artist, event, venue and distance is a seeded, hardcoded simulation, and "near you" is staged rather than measured. A docs site proves a router works; an app like this proves it holds up under pressure — a player that never stops, code-split routes, reactive URL state, and shared-element animations, all in one stateful shell.

</TextBlock>

<TextBlock title="One shell, three ways to discover">

Everything lives inside a single persistent frame: a top bar with search and an activity bell, a "For you" sidebar on desktop, the routed content, and a footer that holds the player (with a mobile tab bar replacing the sidebar on small screens). A segmented control switches between three routed lenses over the same near-you dataset:

- **Artists** — sorted by (simulated) distance (*"0.9 km · May 10"*), each card with a follow heart, switchable between immersive, list and grid layouts.
- **Events** — every upcoming show as its own card; also the mobile "Events" tab.
- **Map** — those same events placed geographically on a real interactive map.

They're not three bolted-on features — they're three routes over one data model, sharing a sticky header. Tapping any artist or event navigates to a full detail page.

</TextBlock>

<TextBlock title="The player that never stops — Routini's optional Outlet">

The trick that makes the whole app feel like a product is that the player keeps playing while you browse. That's a direct consequence of a Routini design decision: `<Outlet>` is optional, and layout is the consumer's call. The player and navigation live *outside* the Outlet, so navigation only swaps the page — the audio element is never in the part of the tree that unmounts:

```tsx
import { Router, Outlet } from "routini";

export default function App() {
  return (
    <Router routes={routes}>
      <TopBar />
      <main>
        <Outlet />   {/* only this swaps on navigation */}
      </main>
      <Player />     {/* lives outside the Outlet → keeps playing */}
      <BottomNav />
    </Router>
  );
}
```

Playback state (current song, queue, volume) lives in a small store, and the player renders in two layouts — a compact mobile bar and a fuller three-column desktop version, both on a Radix slider — with an always-reserved artwork slot so the footer never jumps.

</TextBlock>

<TextBlock title="Detail pages, and the morph between them">

Tap an artist and their feed photo, name and next-show date **morph** into the hero at the top of their page — a real shared-element View Transition, matched by `view-transition-name`, not a fade. From there the page is plain content: a tracklist, upcoming shows, co-performers computed from the shared event lineups rather than hand-authored.

The event page carries the same trick further: its hero uses a blurred, full-bleed copy of the poster behind the sharp artwork, and the identical `poster-<id>` name is shared between the events grid, the map popups and this hero — so all three morph into each other, one animation vocabulary driven entirely by matching transition names, not a library.

</TextBlock>

<TextBlock title="The map — the best argument for a pathname-only store">

The Map lens renders one pin per **venue** so co-located shows don't stack, and hovering a pin opens a themed popup built from the same card used elsewhere (so its poster morphs into the event hero too); when a venue hosts several shows, a small `‹ 1/2 ›` control cycles them in place.

The interesting part is the URL. The current viewport — `?lat&lng&z` — is written to the query string on every pan and zoom through Routini's `useSearchParams`. Because Routini's location store is **pathname-only by design**, writing that query never remounts the expensive Leaflet instance underneath it. A router whose store tracks the whole URL would tear the map down and rebuild it on every drag; here it just updates, quietly. It's the single clearest, hardest-to-fake demonstration of that architectural choice in the whole project.

</TextBlock>

<TextBlock title="Follow, and an activity feed with a reason to exist">

A heart on the feed and every artist page toggles a persisted follow, and from those follows the app derives a "For you" activity feed — new shows and releases from artists you follow, in the desktop sidebar and behind the mobile bell. These rows intentionally skip the View Transition (a circular avatar can't cleanly morph into a horizontal hero the way the feed's rectangular artwork does — knowing when *not* to animate is part of the design), and the page itself replaced an earlier notifications master–detail pattern that, under Routini's flat routing, only ever worked as a workaround: an honest signal of where the router's ceiling actually is.

</TextBlock>

<TextBlock title="How Sona exercises Routini">

Every capability the router advertises gets used here under realistic conditions:

- **Lazy + preload** — every route below the eager Artists feed is code-split and preloads on link hover, so navigation feels instant instead of flashing a loader.
- **`errorFallback`** — a custom fallback tells a failed chunk load (a stale deploy) apart from an ordinary render error and offers the right recovery for each: "Reload" for a stale chunk, "Try again" for everything else, plus a `<Link>` back to the feed either way.
- **Shared-element View Transitions** — the feed→artist and poster→event morphs, wired with nothing but matching `view-transition-name`s.
- **`useParams`** drives the artist and event pages; **`useLocation`** decides when the sidebar drops for a full-width layout and which lens is active; **`<Navigate>`** handles the root redirect to `/artists`.
- **`useSearchParams`** keeps the map's viewport in the URL without remounting it.
- **`scrollRestoration`** — scoped to `AppLayout`'s own scrolling `<main>` via `scrollContainer` rather than the window: switching lenses starts each at the top, and hitting Back into a list restores exactly the scroll position you left it at.
- **Optional `<Outlet>`** is what lets the player persist across every navigation.

Under the UI there's no server at all — 18 artists, 14 events and 12 venues come from a seeded generator and are imported statically, so "performing soon with" and "other events at this venue" are *derived*, distances are assigned rather than measured, and the dataset is stable across regenerations. Songs are real tracks, not placeholder audio; theme is a `data-theme` toggle applied before first paint so there's no flash.

</TextBlock>

<TextBlock title="Where it stands">

Sona proves Routini is more than enough for a stateful, single-layout app, and that its View-Transition and URL-state stories are genuinely strong. It's just as useful for what it *exposes*: the persistent-player-outside-`<Outlet>` pattern relies on Routini having exactly one `<Outlet>` per app — there's no way yet to nest a second layout, with its own outlet, inside the first, the way a settings or admin section often needs its own persistent chrome nested inside the main shell. That's the strongest in-app case for Routini eventually growing nested routes. A few of the router's exports also stay unexercised here (`navigate()`, `preload="render"`/`"viewport"`), so it isn't a complete showcase yet.

As a product, Sona is a front-end prototype — deployed and public, with no backend behind it yet. Real geolocation instead of simulated distances, a real data layer, a submission surface for independent artists, and RSVPs with real ticket links are the natural next steps if it grows into a real service. But as a case study, it's already succeeded at what it set out to do: put a 3.2 KB router through a genuinely demanding, stateful SPA and watch it hold up without compromise.

</TextBlock>
