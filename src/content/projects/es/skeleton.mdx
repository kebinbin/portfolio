<TextBlock title="Por qué la construí">

Durante años, mi instinto cuando un layout se portaba mal era el mismo: ponerle un `background` o un `border` temporal a un puñado de elementos para que las partes invisibles — wrappers vacíos, niveles de anidamiento, la caja que calladamente añade un margen — se hicieran visibles mientras editaba. Funciona, pero es un fastidio: elegir colores arbitrarios, añadir contornos, seguir trabajando y luego acordarse de quitarlo todo antes de hacer commit, para empezar de nuevo en el siguiente componente.

**Skeleton Layout convierte ese hábito en un botón de la barra de herramientas.** Donde las DevTools de Chrome inspeccionan un elemento *seleccionado* (y necesitan su panel abierto), esto pinta la *página entera* de una sola vez y se mantiene fuera del camino — fijada junto al editor de código, sin necesidad de seleccionar nada. No pretende reemplazar las DevTools; es su acompañante persistente y con vista de conjunto. El diseño estuvo acotado por restricciones estrictas desde el inicio: nunca añadir clases, atributos ni estilos en línea a la página; nunca cambiar las dimensiones del layout; que sea reversible en un clic; y pedir la menor cantidad de permisos posible.

</TextBlock>

<TextBlock title="Colorear la página entera con CSS, no con JavaScript">

La decisión central — de la que cuelga todo lo demás — es que la visualización son **selectores de CSS generados**, no un script que recorre el DOM añadiendo clases. El modo por profundidad emite reglas moldeadas por el nivel de anidamiento:

```js
function depthSelector(depth) {
  return `:where(:root${" > *".repeat(depth)})`
}
```

Como es CSS, cualquier elemento que la página renderice *después* queda estilizado gratis — no hace falta un `MutationObserver` re-etiquetando nodos nuevos solo para mantenerlos coloreados. Los overrides se reparten entre los orígenes reales de la cascada de Chrome en vez de esconderse tras un muro de `!important`: las reglas base entran como `AUTHOR`, los overrides forzados por el usuario como `USER`, así los interruptores de "sobrescribir los colores de la página" se corresponden con cómo resuelve la cascada de verdad.

```js
export function buildStyleInjections(candidate) {
  const { style } = normalizeConfig(candidate)
  const rulesByOrigin = { AUTHOR: [], USER: [] }
  const addRules = (rules, override) => {
    rulesByOrigin[override ? 'USER' : 'AUTHOR'].push(...rules)
  }
  addRules(backgroundRules(style, style.overrideBgColor), style.overrideBgColor)
  addRules(borderRules(style, style.overrideBorder), style.overrideBorder)
  addRules(textRules(style, true), true)
  return Object.entries(rulesByOrigin)
    .filter(([, rules]) => rules.length > 0)
    .map(([origin, rules]) => ({ origin, css: rules.join('\n') }))
}
```

Dos detalles se ganaron su lugar. La estructura se dibuja con **contornos (`outline`), no con bordes**, y un `outline-offset` negativo — un borde cambiaría las dimensiones de la caja y provocaría reflow, arruinando el propósito. Y una vez que la página quedó cubierta de reglas comodín, los *propios* tooltips de la extensión quedaban atrapados por ellas; la solución fue excluir cada elemento personalizado interno de los selectores generados, no parchear un borde suelto.

<TextBlock title="Tres maneras de mirar un layout">

El mismo motor impulsa tres modos, elegibles desde la barra de herramientas o un submenú contextual:

- **Full visualization** — tintes de fondo por profundidad o por posición entre hermanos (una paleta editable de seis colores o monocromo), contornos estructurales y texto con contraste automático opcional.
- **Outline only** — deja en paz los colores de la página y muestra la estructura mediante contornos, para cuando el tinte ocultaría lo que estás inspeccionando.
- **Hover inspector** — sin tinte alguno; pasa el cursor para leer el modelo de caja de un elemento.

Los ajustes viven en el **panel lateral** de Chrome, no en una pestaña aparte, así la página que estudias permanece a la vista mientras afinas la paleta. Y cambiar de modo nunca te cuesta tu personalización: tu paleta y opacidad de Full Visualization se guardan en un `fullStyle` separado, así que pasar a Outline o Inspector y volver restaura exactamente lo que tenías.

</TextBlock>

<TextBlock title="El inspector — leer el modelo de caja sin tocar el DOM">

El inspector al pasar el cursor reporta etiqueta, id, dimensiones, profundidad, `display`, `box-sizing`, estado de overflow, el modelo de caja completo de los cuatro lados, pertenencia a flex/grid, contexto de apilamiento, `z-index` y más — y todo ello sin mutar el elemento inspeccionado. En su lugar monta sus overlays y su tooltip dentro de un host de **Shadow DOM cerrado** añadido al documento, para que el CSS de la página no pueda meterse dentro y las reglas comodín de la extensión no puedan salir:

```js
const host = document.createElement('skeleton-layout-element-inspector')
const shadow = host.attachShadow({ mode: 'closed' })
shadow.append(style, ...overlays, tooltip)
document.documentElement.append(host)
```

La hoja de estilos del overlay abre con `all: initial !important` para sacudirse los estilos heredados de la página, las posiciones se programan con `requestAnimationFrame` y el tooltip se ajusta a los límites del viewport. La clasificación del layout vive en su propio archivo sin dependencia del DOM para poder probarse en unit tests fuera de una página real. La pieza más delicada fue contar las pistas del grid: no puedes simplemente partir `grid-template-columns` por espacios, porque `repeat()` y los nombres de línea anidan su propia sintaxis — así que lleva un pequeño parser que rastrea la profundidad de corchetes y paréntesis.

</TextBlock>

<TextBlock title="Vista previa en vivo sin corromper el estado guardado">

Editar los ajustes se previsualiza al instante sobre la página en vivo — pero una vista previa nunca debe convertirse calladamente en tu configuración guardada, y una versión temprana se equivocaba en esto de una docena de maneras (la opacidad revirtiéndose, borradores de paleta perdidos al hacer scroll, previews abandonadas al cerrar el panel). La solución fue modelar tres fases distintas — **saved**, **draft** y **previewed** — en un objeto `SettingsState` que posee cada transición y devuelve copias normalizadas, para que quien lo llame no pueda mutar el estado guardado a través de una referencia suelta:

```js
switchMode(mode) {
  if (!QUICK_MODES.includes(mode)) return this.draft
  const fullStyle =
    this.#draft.style.mode === 'full' ? this.#draft.style : this.#draft.fullStyle
  const style = mode === 'full' ? fullStyle : presetConfigForMode(mode).style
  return this.updateDraft({ style, fullStyle })
}
```

El panel lateral abre un puerto con nombre `settings-preview`; las solicitudes de preview se hacen con debounce (120 ms), se etiquetan con IDs y se serializan en una cola de promesas. El service worker marca cada pestaña con un `previewOwner`, así un panel no puede pisar la preview de otro, y una desconexión revierte cualquier preview que aún fuera suya. Guardar es una ruta de commit aparte — cerrar el panel descarta una preview sin guardar en vez de filtrarla al almacenamiento.

</TextBlock>

<TextBlock title="Reversible por construcción — insertar antes de eliminar">

Apagar la extensión debe *no* dejar rastro, lo que suena trivial hasta que descubres que `chrome.scripting.removeCSS()` exige exactamente el mismo texto CSS **y** el mismo origen de cascada usados al insertarlo. Así que el service worker guarda el conjunto exacto de inyecciones generadas en `chrome.storage.session`, indexado por id de pestaña, y ante un cambio de ajustes hace un diff de los pares `{ css, origin }` viejos y nuevos. El orden importa: el CSS nuevo entra *antes* de que salga el viejo, para que la página nunca parpadee sin estilos a mitad del cambio.

```js
// Insert replacements first so the page never renders without an active
// visualization between settings changes.
for (const injection of additions) {
  await chrome.scripting.insertCSS({
    target: { tabId },
    css: injection.css,
    origin: injection.origin,
  })
  inserted.push(injection)
}
await setTabState(tabId, injections /* … */)
await removeInjections(tabId, removals)
```

Un lock de promesa por pestaña serializa todo — un clic en la barra, una actualización de ajustes, un evento de navegación y una solicitud de preview no pueden competir — y un fallo parcial revierte el CSS que acaba de insertar dejando intacta la visualización que ya funcionaba. Como los service workers de Manifest V3 se detienen y reinician a su antojo, el badge de la barra (`ON` / `OL` / `IN`, o un `!` naranja cuando Chrome bloquea la inyección) siempre se reconstruye desde el almacenamiento de sesión en vez de mantenerse en memoria.

</TextBlock>

<TextBlock title="Diagnóstico de overflow, honestamente etiquetado como experimental">

Un diagnóstico aparte y opcional busca overflow horizontal — el clásico bug de "¿por qué hay una barra de scroll?". Marca en rojo el overflow probable a nivel de documento y en ámbar el posible recorte, dibujando cada marca sobre una **única superficie Canvas 2D** dentro de un Shadow DOM cerrado en lugar de crear un nodo de overlay por candidato. Está acotado a propósito: un presupuesto de escaneo de 20 ms, topes de 12.000 elementos escaneados / 1.000 candidatos / 300 marcas dibujadas, y re-escaneos con debounce ante mutaciones y al quedar quieto el scroll.

La primera versión era demasiado ansiosa — marcaba texto en línea más largo que su caja de línea, contenedores de scroll intencionales, tipografía decorativa grande. Así que el clasificador se afinó para separar el overflow *confirmado* de la página del recorte *posible* e ignorar los casos intencionales comunes. Pero la intención de un overflow no puede leerse solo desde la geometría, así que se queda etiquetado como **experimental** y el conteo es una pista, no un veredicto.

</TextBlock>

<TextBlock title="Una superficie pequeña, y la menor cantidad de permisos posible">

El manifest pide cinco permisos — `activeTab`, `contextMenus`, `scripting`, `sidePanel`, `storage` — y declara **cero** `host_permissions`. Nada se ejecuta en un sitio hasta que invocas la extensión ahí, y los content scripts de diagnóstico se inyectan solo cuando su función está activa; no hay content scripts estáticos sentados en cada página. Las preferencias se sincronizan vía `chrome.storage.sync`; el estado efímero por pestaña vive en `chrome.storage.session`. No hay telemetría, ni analítica, ni contenido de página que salga del navegador — lo que también significa que no tengo datos de uso, un intercambio deliberado.

Todo es JavaScript, HTML y CSS puros, **sin paso de build ni dependencias en tiempo de ejecución** — cerca de 3.900 líneas de código de producción, 51 pruebas automatizadas (con el `node:test` nativo de Node), empaquetadas en un archivo **de 15 ficheros y ~35 KB** por un script de release propio que construye un ZIP *determinista* (timestamps fijos, rutas ordenadas, deflate nivel 9) y se niega a publicar si el manifest y el package no coinciden en versión, si se cuela un `host_permissions`, o si encuentra `eval`, `new Function` o una etiqueta de script remoto.

</TextBlock>

<TextBlock title="En qué punto está">

Skeleton Layout es un **release candidate en la v0.3.0**, plenamente usable como extensión desempaquetada pero aún no en la Chrome Web Store — no hay release etiquetado, las capturas de la tienda y la grabación de demo no están hechas, y todavía no tiene usuarios públicos ni reseñas. También es honesto sobre su techo: el CSS inyectado no cruza los límites del Shadow DOM, el target de scripting actual omite los iframes, los pseudo-elementos no se colorean como nodos propios, y el anidamiento más allá de la profundidad 64 deja de recibir un color nuevo. Es solo para Chrome (116+, por la API del panel lateral), y la matemática de contraste automático compara contra el color de la paleta generada, no contra el resultado compuesto una vez que un tinte translúcido se mezcla con la página — así que es una heurística fuerte, no una cifra WCAG garantizada.

El camino a un lanzamiento real es sobre todo validación, no funciones: correr el ZIP empaquetado en un perfil limpio, recorrer la lista de QA manual en sitios reales, grabar la demo, etiquetar `v0.3.0` y enviar — primero a testers de confianza. Después de eso, los reportes de usuarios reales decidirán si la detección de overflow se gradúa, se rediseña o se elimina.

</TextBlock>
