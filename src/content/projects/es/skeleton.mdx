<TextBlock title="Por qué la construí">

Durante años, cuando un layout se comportaba mal, recurría a la misma solución: fondos y bordes temporales que hacían visibles los wrappers vacíos, los niveles de anidamiento y el espaciado inesperado. Funcionaba, pero cada sesión de depuración comenzaba con CSS arbitrario y terminaba recordando que debía eliminarlo.

**Skeleton Layout convierte esa solución temporal en un botón de la barra de herramientas.** Chrome DevTools es excelente para inspeccionar un elemento seleccionado; Skeleton mantiene la *página completa* visible como un mapa estructural mientras el navegador está junto al editor. Funciona como un complemento persistente y con vista de conjunto a DevTools. Fijé cuatro restricciones antes de escribir código: nunca añadir clases, atributos ni estilos en línea a la página; nunca cambiar las dimensiones del layout; hacer que cada cambio sea reversible en un clic; y solicitar el menor acceso posible.

</TextBlock>

<TextBlock title="Colorear la página entera con CSS, no con JavaScript">

Construí la visualización a partir de **selectores de CSS generados** en lugar de un script que recorre el DOM añadiendo clases, y el resto de la arquitectura se desprende de ahí. El modo por profundidad genera reglas según el nivel de anidamiento:

```js
function depthSelector(depth) {
  return `:where(:root${" > *".repeat(depth)})`
}
```

Como el navegador evalúa esos selectores continuamente, los elementos renderizados más tarde quedan incluidos sin que un `MutationObserver` tenga que volver a etiquetar el DOM. Los overrides utilizan los orígenes de cascada de Chrome en lugar de depender de una pared de `!important`: las reglas base se insertan como `AUTHOR` y los overrides solicitados por el usuario como `USER`. Los ajustes se corresponden así con la manera en que la cascada resuelve los estilos.

```js
export function buildStyleInjections(candidate) {
  const { style } = normalizeConfig(candidate)
  const rulesByOrigin = { AUTHOR: [], USER: [] }
  const addRules = (rules, override) => {
    rulesByOrigin[override ? 'USER' : 'AUTHOR'].push(...rules)
  }
  addRules(backgroundRules(style, style.overrideBgColor), style.overrideBgColor)
  addRules(borderRules(style, style.overrideBorder), style.overrideBorder)
  addRules(textRules(style, true), true)
  return Object.entries(rulesByOrigin)
    .filter(([, rules]) => rules.length > 0)
    .map(([origin, rules]) => ({ origin, css: rules.join('\n') }))
}
```

Dos detalles protegen la página inspeccionada. La estructura se dibuja con **contornos (`outline`), no con bordes**, utilizando un `outline-offset` negativo; los bordes cambiarían las dimensiones de las cajas y provocarían reflow. Los selectores comodín también excluyen cada elemento personalizado interno, manteniendo los tooltips y overlays de la extensión fuera de la visualización.

</TextBlock>

<TextBlock title="Tres maneras de mirar un layout">

El mismo motor impulsa tres modos, disponibles desde la barra de herramientas o el menú contextual:

- **Full visualization** — tintes de fondo por profundidad o por posición entre hermanos (una paleta editable de seis colores o monocromo), contornos estructurales y texto con contraste automático opcional.
- **Outline only** — conserva los colores de la página y muestra la estructura mediante contornos, para cuando el tinte ocultaría el contenido bajo inspección.
- **Hover inspector** — sin tinte alguno; el cursor sobre un elemento muestra su modelo de caja.

Los ajustes viven en el **panel lateral** de Chrome, lo que mantiene visible la página inspeccionada mientras se afina la paleta. Las preferencias de Full Visualization se guardan por separado en `fullStyle`, por lo que cambiar a Outline o Inspector y regresar restaura exactamente la paleta y la opacidad configuradas.

</TextBlock>

<TextBlock title="El inspector — leer el modelo de caja sin tocar el DOM">

El inspector reporta etiqueta, id, dimensiones, profundidad, `display`, `box-sizing`, overflow, el modelo de caja completo, pertenencia a flex/grid, contexto de apilamiento y `z-index` sin mutar el elemento inspeccionado. Sus overlays y su tooltip viven dentro de un host de **Shadow DOM cerrado**, aislados tanto del CSS de la página como de los selectores generados por la extensión:

```js
const host = document.createElement('skeleton-layout-element-inspector')
const shadow = host.attachShadow({ mode: 'closed' })
shadow.append(style, ...overlays, tooltip)
document.documentElement.append(host)
```

Usé Shadow DOM en lugar de depender solo de nombres de clase únicos porque la extensión se ejecuta sobre páginas desconocidas, donde resets globales, selectores amplios o reglas con `!important` podrían alterar la interfaz del inspector.

La hoja de estilos del overlay comienza con `all: initial !important`, las posiciones se programan mediante `requestAnimationFrame` y el tooltip se ajusta a los límites del viewport. La clasificación del layout vive en un módulo independiente del DOM para poder probarla de forma aislada. Contar las pistas del grid necesitó un pequeño parser, porque `repeat()` y los nombres de línea anidan su propia sintaxis y dividir `grid-template-columns` por espacios da conteos incorrectos. Los totales de pistas resueltos son lo que el tooltip reporta arriba como `3 tracks` y `1 track`, junto con los gaps, la alineación y la profundidad del elemento.

</TextBlock>

<TextBlock title="Vista previa en vivo sin corromper el estado guardado">

Los cambios en los ajustes se previsualizan de inmediato sobre la página, pero una vista previa nunca debe convertirse silenciosamente en la configuración guardada. Las primeras versiones expusieron varios errores de estado: opacidad revertida, borradores de paleta perdidos y previews que permanecían después de cerrar el panel. Los corregí modelando tres fases explícitas — **saved**, **draft** y **previewed** — en un objeto `SettingsState` que controla cada transición y devuelve copias normalizadas:

```js
switchMode(mode) {
  if (!QUICK_MODES.includes(mode)) return this.draft
  const fullStyle =
    this.#draft.style.mode === 'full' ? this.#draft.style : this.#draft.fullStyle
  const style = mode === 'full' ? fullStyle : presetConfigForMode(mode).style
  return this.updateDraft({ style, fullStyle })
}
```

El panel lateral se comunica mediante un puerto llamado `settings-preview`. Las solicitudes utilizan un debounce de 120 ms, llevan identificadores y se serializan mediante una cola de promesas. Cada pestaña registra un `previewOwner`; al desconectarse, el panel revierte cualquier preview que todavía le pertenezca. Guardar sigue una ruta separada, por lo que cerrar el panel descarta los cambios sin guardar en lugar de filtrarlos al almacenamiento.

</TextBlock>

<TextBlock title="Reversible por construcción — insertar antes de eliminar">

Apagar la extensión no debe dejar rastro. Como `chrome.scripting.removeCSS()` exige exactamente el mismo texto CSS **y** el mismo origen de cascada usados al insertarlo, el service worker guarda cada inyección generada en `chrome.storage.session`, indexada por id de pestaña. Ante un cambio de ajustes compara los pares `{ css, origin }` anteriores y nuevos. El CSS nuevo se inserta *antes* de retirar el anterior, evitando un parpadeo sin estilos entre configuraciones.

```js
// Insert replacements first so the page never renders without an active
// visualization between settings changes.
for (const injection of additions) {
  await chrome.scripting.insertCSS({
    target: { tabId },
    css: injection.css,
    origin: injection.origin,
  })
  inserted.push(injection)
}
await setTabState(tabId, injections /* … */)
await removeInjections(tabId, removals)
```

Un lock de promesa por pestaña evita que las acciones de la barra, las actualizaciones de ajustes, la navegación y las solicitudes de preview compitan entre sí. Un fallo parcial revierte el CSS recién insertado y conserva la visualización anterior. Los service workers de Manifest V3 pueden reiniciarse entre eventos, así que el badge de la barra (`ON`, `OL`, `IN`, o un `!` naranja cuando Chrome bloquea la inyección) se reconstruye desde el almacenamiento de sesión en cada arranque.

No es un sistema de copia y restauración del CSS del sitio; los estilos originales de la página siguen activos debajo, y al eliminar la hoja inyectada por Skeleton, Chrome vuelve a calcular la página con normalidad.

</TextBlock>

<TextBlock title="Diagnóstico de overflow, honestamente etiquetado como experimental">

Un diagnóstico opcional busca overflow horizontal y marca en rojo el overflow probable del documento y en ámbar el posible recorte. Cada indicador se dibuja sobre una **única superficie Canvas 2D** dentro de un Shadow DOM cerrado, lo que evita crear un nodo de overlay por candidato. El escaneo está limitado a 20 ms, hasta 12.000 elementos, 1.000 candidatos y 300 indicadores, con nuevos escaneos mediante debounce después de mutaciones y desplazamientos.

Mi primer clasificador producía falsos positivos con texto en línea, contenedores de scroll intencionales y tipografía decorativa grande. Ahora separa el overflow *confirmado* de la página del recorte *posible* e ignora los casos intencionales comunes. Las etiquetas ámbar `possible overflow-y` y `possible clipped-x` de las capturas de arriba son esa clasificación prudente en acción: cada una nombra el elemento y el eje en lugar de afirmar que hay un error. La geometría no puede revelar la intención con certeza, por lo que la función continúa etiquetada como **experimental** y su conteo debe leerse como una pista.

</TextBlock>

<TextBlock title="Una superficie pequeña, y la menor cantidad de permisos posible">

El manifest solicita cinco permisos — `activeTab`, `contextMenus`, `scripting`, `sidePanel` y `storage` — con **cero** `host_permissions`. Nada se ejecuta en un sitio hasta que la extensión se invoca ahí, y los scripts de diagnóstico se inyectan solo mientras su función está activa. Las preferencias se sincronizan mediante `chrome.storage.sync`; el estado efímero de cada pestaña permanece en `chrome.storage.session`. No hay telemetría ni analítica, y el contenido de la página nunca sale del navegador.

La extensión utiliza JavaScript, HTML y CSS puros, **sin paso de build ni dependencias en tiempo de ejecución**: aproximadamente 4.100 líneas de código de producción y una suite automatizada de pruebas con el `node:test` nativo de Node. Escribí un script de release que la empaqueta en un **archivo determinista de 15 ficheros y ~36 KiB**, con timestamps fijos, rutas ordenadas y deflate nivel 9. El empaquetado falla si las versiones del manifest y el package no coinciden, si aparecen permisos persistentes de host, o si el código contiene evaluación dinámica o scripts remotos.

</TextBlock>

<TextBlock title="En qué punto está">

Skeleton Layout es un **release candidate en la v0.3.0** que puede instalarse hoy como extensión desempaquetada. El archivo de distribución, la documentación, la política de privacidad y el sitio público están listos; antes de la primera publicación en la Chrome Web Store quedan las pruebas en un perfil limpio, los recursos de la ficha de la tienda y el envío a testers de confianza.

Los límites actuales están claros: el CSS inyectado no puede cruzar los límites del Shadow DOM, los documentos dentro de iframes se omiten, los pseudo-elementos no se colorean de forma independiente y el coloreado por profundidad termina en el nivel 64. Skeleton es exclusivo para Chrome, 116 en adelante por la API del panel lateral. El contraste automático es una heurística: compara contra el color generado de la paleta, no contra el resultado compuesto una vez que un tinte translúcido se mezcla con la página, así que no es una cifra WCAG garantizada.

Lo que queda es validación: probar el ZIP empaquetado en un perfil limpio y en sitios representativos, preparar los recursos de la ficha de la tienda, etiquetar `v0.3.0` y enviarlo a testers de confianza. Sus comentarios determinarán si la detección de overflow se gradúa, cambia de dirección o se elimina.

</TextBlock>
